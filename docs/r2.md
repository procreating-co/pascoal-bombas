# Cloudflare R2

## O que vive no R2 hoje

Só os **vídeos**. Fotos da galeria ficam em `public/gallery/<slug>/<pasta>/` (commitadas no git,
lidas via filesystem em `lib/gallery-server.ts`) e são otimizadas em tempo real pelo próprio
otimizador de imagens do Next.js (`lib/gallery.ts`'s `optimizedGallerySrc`) — não há upload de
foto para o R2 neste projeto.

R2 é um bucket público (leitura sem autenticação) servido em `https://<hash>.r2.dev/...`. Não há
nenhuma credencial de R2 no código nem em variável de ambiente — o upload de arquivo novo é feito
manualmente pelo painel da Cloudflare (ou `rclone`/`aws s3` apontando pro endpoint R2), fora deste
repositório.

## Convenção de pastas para clientes novos

```
clients/<slug>/videos/<arquivo>.mp4
```

Cada cliente novo sobe os vídeos dentro da própria pasta no bucket. Isso existe para não misturar
arquivos de clientes diferentes na raiz do bucket conforme o número de projetos cresce.

**Exceção histórica: Pascoal.** O bucket da Pascoal já estava em produção antes deste padrão
existir — os 5 vídeos estão soltos na raiz (`data/pascoal/videos.ts` aponta direto pra lá, com
percent-encoding montado à mão nas URLs). Não foi reorganizado: mexer nisso arriscaria quebrar
URLs que já estão em produção, sem nenhum ganho real. Todo cliente **novo** a partir de agora
segue a convenção `clients/<slug>/videos/`.

## `lib/r2.ts` — montando URLs sem percent-encoding manual

```ts
import { r2Url } from "@/lib/r2";

const R2_PUBLIC_BASE = "https://<seu-bucket>.r2.dev/clients/<slug>/videos";

videoSrc: r2Url(R2_PUBLIC_BASE, "Vídeo de Apresentação (Reunião).mp4"),
```

`r2Url(base, filename)` faz o `encodeURIComponent` do nome do arquivo por você — não precisa
copiar uma URL já percent-encoded do navegador nem escrever `%C3%AD` na mão. Usado em
`data/_template/videos.ts`; `data/pascoal/videos.ts` continua com suas URLs manuais originais
(ver exceção acima).

## Proxy de download (`app/api/download/route.ts`)

O atributo HTML `download` só é honrado pelo navegador em links **same-origin**. Como os vídeos
vivem em `r2.dev` (origem diferente do site), um `<a href={videoSrc} download>` direto para o R2
seria ignorado pelo navegador, que abriria o vídeo em vez de baixar. `app/api/download/route.ts`
resolve isso: faz o proxy do arquivo original (mesma qualidade, sem recompressão) através do
próprio domínio do site e define `Content-Disposition: attachment`, forçando o download.

Por segurança, a rota só aceita `src` cujo host termine em `.r2.dev` (`ALLOWED_HOST_SUFFIX` no
arquivo) — não é um proxy aberto para qualquer URL.

## Se um vídeo não aparece

1. Confirme que a URL em `data/<slug>/videos.ts` bate exatamente com o caminho do arquivo no
   bucket (case-sensitive).
2. Abra a URL do vídeo direto no navegador — se der 404 lá, o problema é no bucket/upload, não no
   código.
3. Bucket é público por padrão neste projeto; se um arquivo novo não carrega mas outros do mesmo
   bucket carregam, verifique se ele foi marcado como privado no upload.
